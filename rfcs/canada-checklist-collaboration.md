需求来源：[原任务书](https://mtsyama.github.io/collab-intel-step0/wc/)。本文只讨论如何开始协作，不替代原任务书，也不另造一套产品需求。

## 本次先决定什么

建议先交接现有引擎和三份清单，评估复用成本，再确认开发安排。不要在还没看代码时承诺四周交付，也不必为了讨论先搭一个协作平台。

原提案的三个场景、进度保存、邮件提醒、分享和 Stripe 年费暂作为讨论基线，不表示双方已经批准全部范围。技术选型也只是本地调研推荐，不是已上线方案。

## 请在这几段下面直接批注

### 1. 参与和时间

技术参与方是否参与、每周可投入多少小时：待本人填写。
内容方原提案写每周 10 小时：仍请确认当前是否适用。
是否同时开展 Claude Code 工具方向：待双方确认；本次不默认开启第二项目。

### 2. 交接现有成果

请内容/引擎持有人提供：
- 单文件清单引擎的仓库路径或文件。
- 三份清单的源文件和已核对的官方链接。
- 哪些内容已经成稿，哪些仍是示例或待核。

不需要提供任何账号密码、Cookie、令牌或真实用户数据。

### 3. 第一轮交付

建议先验收“选择一个示例场景 → 保存进度 → 另一会话继续 → 分享后不带个人进度”的本地闭环。
这只是实施顺序，不是删除第一版的邮件和支付需求；要改变最终范围，需双方明确确认。

### 4. 两个需要先讲清的限制

- 每月 USD 20 的预算是否包括域名、税费和支付手续费？免费邮件存在每日额度，不能据月总量承诺所有高峰提醒准时送达。
- 官网自动监控在原文中既是后续功能，又出现在第三周。建议第一版先人工核对来源，自动化后置，待双方确认。

## 怎样讨论和确认

把本文放进双方选定的 GitHub 仓库，以 Pull Request（修改提案）提交，而不是直接改主分支。使用有仓库写权限的分支；没有权限时先确认协作方式，不默认创建公开副本。

另一方在文件改动视图中对具体段落评论；提出者修改这同一个文件。版本变化由 Git 记录，不需要再复制 v2、v3 网页。评论解决不等于对方同意：重要选择应在正文中写明结论，并由另一方明确确认。

双方认可后再合并；合并表示接受本文最终约定，不表示应用已经完成或授权部署。尚未解决的参与/工时问题不能以“合并了”来代替本人承诺。

## 确认后才建立待办

不用现在生成一大批 Issues。先建这两项，负责人经本人确认后再指定：

1. **交接现有引擎与三份清单**：完成条件是双方能访问非秘密源文件，且成稿/待核状态明确。
2. **评估复用并实现第一个本地闭环**：先检查引擎，再实现上面的最小流程；以合成数据证明保存与隔离，不接真实邮件和支付。

后续任务依据实际评估结果拆分。Discussion 仅在出现新的开放问题时使用；HTML 展示页和自动发布不是开始协作的前置条件。

## 2. 调研说明了什么：不是再做一个中文信息站

| 已有替代 | 本轮公开资料观察 | 对我们的挑战 |
|---|---|---|
| [Welcome to Canada / PeaceGeeks](https://www.peacegeeks.org/welcome) | 免费资源与个性化推荐，部分地区含中文内容 | “有中文”“有加拿大信息”本身不足以成为付费理由；具体提醒和清单能力未试用，不能说它没有 |
| [Canoo](https://canoo.ca/) | 面向新移民的免费 App，文化体验与优惠 | 是相邻用户群的免费产品，不是已经证明的学签/PGWP 流程替代 |
| [IRCC 安居服务](https://ircc.canada.ca/english/newcomers/services/index.asp) | 官方免费服务查找入口，服务适用资格有范围 | 官方信息和服务本就存在；不能假设所有留学生都能使用所有安居服务 |
| 已有清单网页 + 用户自己的日历 | 引擎能力仅来自原任务书描述，代码未看 | 是低成本对照：用户是否真的需要另付年费，而不是拿到内容后自己设提醒？ |

我们的候选差异化是“特定办事场景的经核对步骤、版本变化说明与可靠提醒”，不是“加拿大信息大全”。这是待验证假设，不是已证明的竞争优势。

原任务书证明用户会为政府手续或顾问花钱，但尚未证明会为清单订阅付费。四周指标中的“付费或订阅提醒超过 50 人”应拆开记录：付费人数、确认提醒订阅人数、两者去重并集。免费订阅达到目标，不等于年费模式成立。

**请讨论：用户最愿意付费的是哪一项——步骤内容、避免遗漏、跨设备进度还是规则更新？用什么真实行为验证，而不是只看收藏数？**

## 3. 为什么暂时推荐这套技术，而不是直接照抄任务书

| 方案 | 好处 | 主要限制与当前判断 |
|---|---|---|
| Softr 无代码门户 | 已有数据库、登录和工作流，减少部分代码 | 本轮价格页用户额度与 USD 20 预算不匹配目标验证规模；不推荐作为完整主系统 |
| Cloudflare + Supabase Auth/Postgres | 托管认证和关系库，减少部分维护职责 | 免费项目存在不活跃暂停机制；Pro 起价 USD 25，尚未加邮件已超预算；预算放宽后仍值得考虑 |
| Workers + D1 + Better Auth | 配合原建议，少一个数据库服务；认证用成熟库 | 库不等于托管服务，我们承担会话、限流、迁移和运行维护；必须本地验证 |
| 先不做后端，复用网页与用户日历 | 工程最少、容易撤回 | 不能完成跨设备、平台邮件提醒和订阅权益的完整承诺；可作验证对照 |

暂推荐 Workers + D1 + Better Auth，邮件 Resend，Stripe Checkout 年订阅；前端先看已有引擎再决定。只自建清单内容、版本化进度和提醒编排，不自建认证协议、发信基础设施或支付系统。

Better Auth 的官方发布说明支持 D1，魔法链接也有官方插件，但本轮没有运行兼容性实测、依赖版本锁定或安全验证。推荐表示“值得先做本地验证”，不是“栈已定且能生产运行”。来源和迁移代价见配套调研。

每周约 40 小时并不改变先买成熟能力的原则。时间应优先用于产品闭环和可靠性，而不是多造认证、后台平台或自动监控系统。

**请讨论：是否按这条路线先做本地验证？若少量增加月费能明显减少维护，USD 20 是不可突破的硬约束，还是可以重新讨论？**

## 4. 两个成本问题需要明确回应

### 邮件：月量够，不代表同一天能发完

[Resend 官方额度](https://resend.com/docs/knowledge-base/account-quotas-and-limits)：免费档每日 100 封、每月 3,000 封，登录邮件和提醒共同消耗额度。

规划示例：300 用户每月各两次登录、三个提醒，共 1,500 封，月量够；同一天 300 人登录或到期则超日额度。限流可以管理流量，但不能靠无限延后提醒假装解决可靠性。

本轮价格情景：Workers 付费基础档约 USD 5/月，Resend Pro 起价 USD 20/月，合计约 USD 25，尚不含域名、税和其他用量。不是说一定要买这两项，而是不能承诺“选免费档就天然满足规模、成本和准时送达”。

### 年订阅：不仅是刷卡手续费

[Stripe 加拿大定价](https://stripe.com/en-ca/pricing)的标准境内卡费率为 2.9% + C$0.30，Billing 按用量模式另有 0.7%。年订阅 C$19 / C$29 的上述费用示例约为 C$0.98 / C$1.34，未含国际卡、汇兑等，经营主体所在地也尚未确认。

**请讨论：月预算是否含域名摊销、税和支付手续费？免费邮件额度不足时，选择限制验证规模、重新选邮件方案，还是批准增加预算？当前没有自动升级或开通服务的授权。**

## 5. 内容风险可能比写代码更关键

PGWP 的“180 天”不是完整的资格判断。[IRCC 申请页](https://www.canada.ca/en/immigration-refugees-citizenship/services/study-canada/work/after-graduation/apply.html)还涉及身份、学签有效期、恢复身份及等待期间工作条件。退回、拒签、补发、续签也不能合并为同一补救流程。

因此，不能只根据一个用户日期输出“你能申请/你可以工作”的结论；不能因页脚写“非法律建议”就把个体判断当一般信息发布。内容要有来源、适用范围、版本、核对日期和待核状态，不存证件或个案材料。

[CRTC 指引](https://crtc.gc.ca/eng/com500/guide.htm)涉及商业电子消息的同意、发送者身份和退订。本轮未完成法律适用性审查，提醒、产品更新、推广需分别设计，不宣称已经合规。

**请讨论：谁负责核对和批准三份内容？发现官方规则变化时谁能暂停或标记待核？原任务书的自动监控建议第一版后置、先人工核对，是否认可？**

## 6. 从调研进入实施：先补证据，再按闭环推进

请现有成果持有人提供引擎、三份清单的非秘密源文件与官方链接，并区分成稿、示例、待核。不需要账号密码、Cookie、令牌或真实用户数据。

建议第一轮顺序：

1. 检查引擎可复用部分，核对一个场景的内容合同；补查竞品实际流程和目标用户付费动机。需要账号或对外访谈的动作另行确认。
2. 合成数据闭环：“选场景 → 登录 → 保存进度 → 另一会话继续 → 分享不含个人进度”。验证账号隔离和内容版本变更。
3. 假邮件验证日期边界、重复任务、改日期和退订；支付 fixture 验证重复/乱序事件与权益，不接真实收款。
4. 根据实际进度确认三场景、邮件和年费的实现排期；上线前再满足内容核对、隐私、经营主体与服务授权条件。

这是实施顺序，不是删去 v0.1 的邮件和支付，也不是保证以上四项各用一周。团队在引擎交接和首个闭环后再做有依据的交付估计。

**请讨论：是否先按这条顺序推进？引擎和内容交接能否作为第一个明确待办？**
